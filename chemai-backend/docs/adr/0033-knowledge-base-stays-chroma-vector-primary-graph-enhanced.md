# ADR-0033: 知识库全 Chroma、向量主导、图谱为增强而非独立召回路

日期：2026-10-27 · 状态：已接受

## 背景

为化学项目建教材知识库（GraphRAG）。参考实现 qiuqiu/teaching-assistant 用 SQLite 单文件栈（FTS5 + sqlite-vec + 客户端 BM25 的混合检索），但 chemai 已有 ChromaDB 在跑；同时 GraphRAG 的"图检索 vs 向量检索"存在路线分叉；题目题库是否入库也在议题内。

## 决策

1. **全 Chroma**：向量存 Chroma（collection `kb_chunks`），不引 FTS5/sqlite-vec 第二套基建。关键词匹配的边角用 Chroma `where_document` 子串兜底；真不够时在客户端加轻量 BM25 重排，不动存储。
2. **向量主导 + 图谱增强**：问答先向量召回 top4，再按命中块的知识点上图取先修链/方程式作附加上下文；图不做独立召回路。出题相反，纯图驱动（先修链控难度阶梯、方程式做素材）。
3. **图谱存 SQLite**（复用 knowledge_points/knowledge_edges，加 edge_type/confidence 列）：图是结构化数据，邻接查询 SQL 足够，不引图数据库。
4. **题目不进知识库语料**：30920 行去重后仅 307 题、171 带解析，量级不足以当语料；降级为挂钩资产——出题归档按 kp_ids、错误率统计回写图谱节点。

## 后果

- 正：少一套存储基建；检索实现薄（一个 query + 一个图邻接查询）；出题与问答共享同一图谱，一次建设两处受益。
- 负：放弃 BM25 意味着纯字面查询（元素符号、化学式片段）依赖向量模型与子串兜底——语料小（几千块）时实测可接受，语料涨到数万块需重估。
- 负：Chroma 无跨库事务，幂等靠指纹先查后写；文档修订的"先删后插"存在中间态窗口，摄取是离线操作可接受。

## 否决项

- SQLite FTS5 + sqlite-vec 全家桶（qiuqiu 同款）：那是无 Chroma 约束下的选型，chemai 已有 Chroma，引第二套存储是负资产。
- Neo4j 等图数据库：几十~几百节点的邻接查询，SQL 足够。
- 题库向量化：结构化字段检索已覆盖其使用方式。
- GraphRAG 全家桶（社区摘要/多跳聚合）：第一期图谱规模与问答场景用不上，先修链+方程式增强已覆盖需求。
