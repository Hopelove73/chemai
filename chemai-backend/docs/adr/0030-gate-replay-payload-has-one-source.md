# ADR-0030: 确认门的重放载荷以数据为唯一真源

**Date**: 2026-04-16
**Status**: Accepted（计划 `openspec/changes/gate-lifecycle/` 批次 2 的 2.4；
用户裁定：批次的 2.6「重放前校验」一并做，且**只做会真正生效的那一处**）

## Context

老师点「批准」之后，系统要执行一个**不可逆动作**（发送学习方案给家长、布置练习、
删题库）。执行哪件、带什么参数，此前有**两个来源**：

| 来源 | 谁在用它 |
|---|---|
| 门那一行（`agent_gates`：`tool_name` + `kwargs`） | **确认卡**——老师看到的内容由它渲染 |
| 进程内的 `guard_state.pending_approval`（`{name, fn, kwargs}`） | **重放**——`_direct_replay_events` 执行的是 `pending["fn"](**pending["kwargs"])` |

两者在各条开门路径上**恰好一致**（草稿门、按次审批、布尔门、打回重开），
但**一致性此前没有任何东西守着**——靠的是"写的时候记得写对"。
门行被改一笔、或者重放载荷换了来源，老师批的和他拿到的东西就悄悄不是一回事，
**且没有任何迹象**。

同一族还有一个更硬的缺口，2026-10-17 实测复现：

> **C1-Q3「有未决门时 agent 的一切工具调用都被拒」在重启后整段失效。**
> 它的判据是**内存里**的 `pending_approval`，而内存随进程一起消失 —— 这是重启的定义。
> 于是老师看着一张还在等他的确认卡（卡片来自库，照常显示），**闸却没了**：
> agent 能直接往下推进，把卡片还等着的那些动作先做了。
> `_rebuild_pending_from_gate` 的存在本身就承认了这个缺口（它专门在「内存 pending
> 已失」时从实体重建），但它只被**重放**那条路调用，**拦不拦得住工具这条路上没人问库**。

## Decision

**门的重放载荷以它那一行数据为唯一真源。** 三处落点：

1. **重放目标从实体构造。** `_direct_replay_events` 优先走
   `_rebuild_pending_from_gate`（即 `gate_service.replay_target`，那个设计好的唯一入口），
   进程内那份只在**没有会话**（纯内存评测）时兜底 —— 那条路压根没有实体可读。
   该函数的裸 `except Exception: return None` 一并换成留痕：读失败时静默返回 None，
   调用方会悄悄退回另一个来源，而"悄悄退回另一个来源"正是本 ADR 要消掉的东西。

2. **开门即钉载荷指纹，重放前校验**（同批次的 2.6）。`open_gate` 的两个分支
   （新开 + 同 `gate_id` 复位重开）都写 `args_hash`（`tool_name` + `kwargs` 的规范化摘要）
   与 `schema_version`；重放前两道都过：
   - ① 门行自己还是开门时那一份吗（挡「卡片的来源被改过」）
   - ② 即将执行的就是批准的那一份吗（挡「卡片与执行脱节」）

   任一道不符即 fail-closed：不执行，把门落 `superseded`，告诉老师重来。
   存量门（指纹为 NULL）放行 —— NULL 是「未记录」（同 `plan_step` 口径），
   把它当"不符"会当场作废库里所有开着的门。

3. **「门开着吗」问记录，不问内存。** 新增 `GuardState.gate_is_open()`：
   每次都查 `get_open_gate`；读不出来返回 `None`，调用方 fail-closed。
   内存里那份判据（`pending_approval`）在同一批次删掉了 —— 只认内存的代价是
   重启后整段失效，而「答案只有一个来源」比省一次本地 SQLite 读重要。

**为什么不做成"只校验、不改来源"**：那样只能说"发现两者漂开了"（fail-closed，
老师重来一次），而**让漂开不可能发生**更好 —— 你不信任的第二个来源，直接不使用它。

## Consequences

- **老师看到的卡片与真正执行的动作，从此是同一个来源**，不是"两边约定写对"。
- 由 1 产生的一处**冗余**（记下来，别当成还能守堤）：重放改用实体之后，
  2.6 的第二道校验（"要执行的就是批准的那一份"）在这条路上**恒真**了。
  它仍有意义（守住将来别的调用面），但别指着它挡"内存与实体漂开"——
  那个洞现在由"只有一个来源"来堵。
- **一处语义变化（测试照出来的）**：重放按门那行的 `tool_name` 经 `_TOOL_BY_NAME`
  解析函数，所以往 `pending_approval` 里塞**假工具**不再作数。生产无影响
  （2.5 保证了门能开 ⇒ 工具必在注册表里，解析出来的是同一个函数）；
  但既有用例里"靠数假工具调用次数"来验「批准两次不执行两遍」的写法失效，
  已改成看**真实效果**（建一个真题库 → 批准后它真的没了 → 第二次绝不能再来一遍），
  比数假工具更硬。
- **由 3 产生的一个直接后果，值得单记：库里那些陈旧的开着门，从"无害的历史行"
  变成了"真的会锁死会话"。** 修之前它们无害（重启后内存为空，闸本来就是松的），
  修之后每个「算数」的陈旧门都会把那个会话的工具全拦掉。
  实测（2026-10-17）：演示库里 41 扇算数的未决门 —— 而**本该每天收敛假门、
  作废超期门的作业从来没挂上**。本 ADR 因此直接催生了 T17（
  `app/scheduler/gate_expiry.py` + `scripts/repair_gates.py`）。
  教训：**把一道闸从松改成紧，得同时清点它现在会拦住谁。**
- **代价**：每次工具调用多一次库读（`gate_is_open`）。SQLite 本地读，实测无感。
- **适用范围**：本 ADR 约束**门的重放载荷**与**门的开闭判据**。
  `guard_state.pending_approval` 这个字段**已随本批次删除** —— channel 侧原先
  读它的 5 条路径（打字语义分类、resume 意图解析、重放兜底等）全部改为问门实体
  （`_pending_from_entity` / `_gate_draft_id` / `replay_target`）。
  "一处按键、两处读"的形状在门这条链上不再存在。
