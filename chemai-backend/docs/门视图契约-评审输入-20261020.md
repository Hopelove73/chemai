## 0. 一句话问题

确认门（teacher 批准/打回/放弃）的**生命周期**（数据）与**会话时间线**（视图）之间**没有定义过契约**，
唯一耦合是 SSE 里一个会丢的 `gate_open` 事件。要评审的就是「这个契约怎么定」。

## 1. 要评审的两个方案（B / C）与一个待删项

| | B：状态驱动 | C：消息化 |
|---|---|---|
| 机制 | 门行 `agent_gates`(status=open) 是唯一真源；聊天页按 `conversation_id` 从 `/api/agent/gates/pending` 取自己那几张卡渲染 | 把「这里有张待批卡」写成会话历史里的一条产物，重开会话顺历史恢复 |

## 2. 行业调研结论（四条主流实现，已核实原文）

| 项目 | 声明方式 | 停下的是什么 | 决策怎么回到流程 |
|---|---|---|---|
| **LangGraph / deepagents** | `interrupt_on={tool: True\|Config}` → `HumanInTheLoopMiddleware`（**必须**有 checkpointer） | 图节点中断 | `Command(resume=...)` 恢复原 run |
| **OpenAI Agents SDK** | `@tool(needs_approval=True)` 或判定闭包（参数解析不干净即 fail-closed 转人工） | run 级 interruption，`RunState` 可序列化落盘 | 在 `RunState` 上批/拒后 resume；嵌套 agent 的审批冒泡到外层 run |
| **Pydantic AI** | deferred tools（审批 / 外部执行两种） | **结束本次 run**，产出 `DeferredToolRequests` | 同进程 handler 就地续跑；或**开新 run** 带 `DeferredToolResults`（新 run_id，靠 conversation_id 关联） |
| **Vercel AI SDK** | tool 上 `needsApproval` | **不中断 run**，把审批做成**消息流里的一个 part**（`tool-approval-request`） | 前端 `addToolApprovalResponse` 回填后继续 |

### 三条共识（也是本仓偏离的地方）

1. **审批请求必须可持久化**（消息 part / checkpoint 里的 pending interrupt / 可序列化 RunState）。
   **没有一家靠"流里发个 event 让前端立刻渲染"** —— 流一断就没了。
2. **「停下」= 结束一次 run/节点，不是伪造模型回复。**
3. **决策普遍四值**：LangGraph 的 `allowed_decisions = approve / edit / reject / respond`。本仓只有三值
   （approve / reject / abandon）——「改一句再发」必须打回重走。

> 附带发现：deepagents 有专门的 `PatchToolCallsMiddleware`，用于修「run 在 tool 返回前被打断、
> 历史里留下没有 result 的 tool_call」。本仓 `_repair_tail_toolcall_gaps` 在做同一件事 —— 这是该架构的通病。

## 4. 候选契约（请评审裁定这三条是否成立）

**① 视图是投影，不是副本。**
卡的唯一真源是门行；会话里只存**指针**（gate_id + 位置），内容回表查。
→ 成立则 B 是自然结果；C 的唯一安全形态是"存指针不存内容"。

**② 回合边界必须显式。**
门开出 = 该轮**正常结束**（不是异常、不是被拦），后续工具调用数为 0；
结束事件带 `gate_id`；恢复走确定性重放（ADR-0013/0015 已做对，**不要动**）。

**③ 决策四值。**
approve / edit / reject / respond。补 `edit` 意味着门数据模型要加字段（改后的 payload 存哪）。

## 7. 验收标准（"完成度高"的判据）

1. **三态一致**：断流 / 重启 / 刷新，卡都在、都能点、状态正确。
2. **零撞墙**：门开出后本轮后续工具调用数 = 0（不是 N 次被拦，也不是一段假回复）。
3. **时间线完整**：生成 → 待批 → 批准/打回/改后发 → 已发送，五态在时间线上都在，刷新后仍是同一部史。
4. **四值可用**：approve / edit / reject / respond 各有端到端用例。
5. **可回放**：任一决策能顺 `gate_id` 追到「谁批的、批的什么参数、重放结果如何」。

## 10. 评审订正（2026-10-20，eng review 回填）

下面三处是评审过程中**核对代码后**发现的原文错误。保留原段落不动，把订正记在这里，
以免后续引用时把错的当成对的。

1. **§3.1 的 DOM 证据不成立。** 原文用 `data-gate-id` 节点数为 0 作为「确认卡没渲染」
   的铁证，但**这个属性全仓不存在**（grep 只有两处命中，都在文档里）。数出 0 是必然的，
   与卡渲不渲染无关。A5 的定性需要重做证据：`需要确认` / `发送给学生` 两个文案计数仍可用，
   `data-gate-id` 这一条作废。
2. **§1 表格里 B 的读点写错了。** `/api/agent/gates/pending` 是**用户维度**
   （`pending_gates(db, user_id, kind)`），没有 `conversation_id` 参数；它的 item 也**不含**
   `draft_id` / `version`，而决定必须带这两个字段。拿它渲染聊天页的卡会得到一张点不动的卡。
   会话维度的正确读点是 `gate_service.get_open_gate(conversation_id)`，今天的消费方是
   `/chat/history` 的 `gate` 段。
3. **§5 代码坐标表有一行过期。** 「门卡当前只从 SSE `gate_open` 渲染」不准确：
   `frontend/src/pages/teacher/ChatPage.tsx` 早已按 `gate_id ?? draft_id` 从历史恢复门卡。
   缺的不是「恢复能力」，是「什么时候重读」—— 正常结束不复读，见 ADR-0031 ②。

另外补一条原文没问、但评审认定是 A5 真因的：**活流里从来没有下发过「已经开着的门」**。
`gate_open` 只在工具结果带 `approval_needed` 时发；门已开时模型再撞门走 `_waiting_out`，
不产生任何门事件。所以 A5 的现场不是「卡画错了」，是「这条通路压根没送卡」。
