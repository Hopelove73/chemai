# 管理后台建设方案（2026-11-04）

> 调研依据：对 chemai-backend 现状、qiuqiu（小糖表演台）、teaching-assistant（智智助教台）三个项目的管理后台对比调研。
> 本文取代 `docs/权限与班级管理设计_20260422.md` 中未实施的 admin.html 设计（第七章 Phase 2），并落地 rbac-enforcement HANDOFF 第 269 行记录的「阶段 5 要处理的中间态」。

---

## 0. 结论

**做管理界面，但不做独立后台应用。** 在现有教师端 SPA 内、以「能力清单驱动菜单」的既定机制，新增管理员菜单与页面；所有管理 API 挂在主 FastAPI 进程内。分三期：

| 期 | 主题 | 一句话 |
|---|---|---|
| **P0** | 管理员可用 | 清「403 按钮」账 + 管理员落地页/待办 + 教师审批 + 学校设置 + 操作日志，后端几乎零新端点 |
| **P1** | 内容运营界面 | KB 知识库审校落库界面化，替代 `_reviews.json` + 口头批准；摄取触发视部署环境后置 |
| **P2** | 运营深化 | 深度看板、break-glass 工作台、数据导入向导、LMS 集成持久化 |

---

## 1. 定位与非目标

### 1.1 这个后台服务谁

chemai 是**多角色学校平台**（7 角色，RBAC 已在后端收严完成），不是 qiuqiu/teaching-assistant 那种单人运营的演示产品。本后台的两类用户：

1. **学校管理员（admin / academic_admin）**——日常管理：审批教师入驻、管理账号、重置密码、看操作日志、学校设置。**这是 P0 的用户。**
2. **平台内容团队（super_admin + 开发流程）**——KB 语料/词典/审校包治理。**这是 P1 的用户。**

qiuqiu/teaching-assistant 的后台是「单人驾驶舱」（单 token、零 RBAC、独立进程），形态**不可移植**；可移植的是它的**模式**：审计页、知识库治理（编辑→异步 job→轮询→回收站）、运行时开关、推导式只读看板、明确非目标清单。

### 1.2 非目标（学 qiuqiu ADR-0006 的纪律，先写清楚不做什么）

- **不做独立 admin 进程 / 独立 react-admin 前端**。三个硬理由：
  1. `chemai.db` 被运行中的 uvicorn 锁定（HANDOFF 已知坑 10），另起进程写库必然踩锁；
  2. chroma 删集合与重摄必须同进程（WAL 竞态，HANDOFF 已知坑 3）；
  3. 已有 JWT + 7 角色矩阵 + `menus_for()` 菜单下发 + 前端路由守卫，再建一套单 token 平行体系是开倒车。
- **不做 RBAC 编辑器**。权限矩阵留在代码里（`app/middleware/auth.py`），由测试钉住，不在界面上改权限。
- **后台不触发花钱的 LLM 评测**。`kb_eval` 阈值评测继续走 CLI（开发机）。
- **不提供直改派生数据的入口**。chunk / 向量 / 错误率聚合都是派生数据，界面只改源（语料、词典、审校包）然后触发重建。
- **不做多租户平台看板**。当前部署模型是单校一部署，跨校是 super_admin + break-glass 的事（P2 才做工作台）。
- **学生/家长端不变**。本方案只动员工端 SPA。

## 2. 分期评估（对原始 P0/P1/P2 的三处修正）

原分期方向正确，修正如下：

1. **P0 增加「管理员落地页 + 登录按角色跳转」**。现状 admin 登录后落在 `/chat`（Agent 工作台，教师工具），管理员进来不知道去哪。概览页用推导式只读数据（qiuqiu 已验证的低成本高价值模式），并承载待办（待审批数）。
2. **P0 砍掉「数据导入界面」**。`data_import`（名册/任教/考试导入）是部署期低频动作，API 已存在且可用，界面化推迟到 P2 的部署向导。P0 聚焦**每周都发生**的管理动作：审批、账号、删题库、重置密码、看日志。
3. **P1 的 KB 治理拆两档**。P1a（审校落库界面）是纯 DB 写，无嵌入模型依赖，先做；P1b（摄取触发）依赖 `EMBEDDING_CACHE_DIR` 本地嵌入模型 + 同进程 chroma 操作（HANDOFF 已知坑 1/3），且属开发机场景——若部署机没有模型环境，P1b 永久保持 CLI，界面只做「生成命令供复制」。**且 KB 治理的用户是 super_admin/内容团队，不是学校管理员**，菜单按 `knowledge:update` 下发（仅 admin 镜像 + super_admin）。

## 3. P0 —— 管理员可用

### 3.1 现状账本（P0 要清的）

| 中间态 | 证据 |
|---|---|
| ExamPage 删考试/删题库/删题目按钮对教师 403（`exam:delete`/`exam_bank:delete` 仅 admin 有） | rbac HANDOFF:269 |
| StudentsPage 重置密码按钮对教师 403（端点门 `student:update`，教师只有 `student:read`） | `app/api/user.py:637` |
| 教师入驻审批（approve/reject）**没有任何界面** | API 存在：`app/api/teacher_application.py` |
| `GET /teacher-applications` 门是 `teacher:read` + 函数体内手写 `role != "admin"`——矩阵外的第二套授权（与阶段 7.1 整改前的 log.py 同款反模式） | `app/api/teacher_application.py:32-36` |
| user.py 的审批/重置密码/调班/删除**不写操作日志**（data_import.py 写，user.py 不写） | `grep OperationLog app/api/user.py` 为空 |
| 操作日志 API（`log:read`，仅 admin）无任何界面消费 | `app/api/log.py:24` |
| admin 登录落地 `/chat`，无管理员菜单 | `frontend/src/pages/teacher/LoginPage.tsx:55` |

### 3.2 菜单与路由注册（机制已就位，只差登记）

后端 `app/middleware/auth.py` 的 `MENUS` 追加（顺序即侧栏顺序，排在教师菜单之后）：

```python
# ── 管理端（2026-11 管理后台 P0）──────────────────────────
# 与教师菜单同一机制：key 由后端下发，展示细节在前端 MENU_REGISTRY。
{"key": "admin_overview", "resource": "school",     "action": "read"},    # admin / academic_admin / super_admin
{"key": "admin_users",    "resource": "class",      "action": "create"},  # admin / academic_admin / super_admin
{"key": "admin_school",   "resource": "school",     "action": "update"},  # admin / super_admin
{"key": "admin_logs",     "resource": "log",        "action": "read"},    # admin / super_admin
```

**P0 不新增任何资源键**——`school`/`class`/`log` 全是既有键，矩阵完整性断言零改动。

前端 `frontend/src/App.tsx`：

- `MENU_REGISTRY` 增加四项（`/admin`、`/admin/users`、`/admin/school`、`/admin/logs`）；
- `ROUTE_MENU` 同步登记；
- lazy import 四个新页面（放 `pages/admin/` 新目录）。

登录跳转：`LoginPage` 登录成功后不再硬编码 `/chat`，改为**按下发菜单列表**：含 `admin_overview` → `/admin`，否则 `/chat`。学生/家长登录路径不受影响（他们菜单为空，走各自移动端入口）。

### 3.3 页面规格（4 页）

**① `/admin` 概览与待办**（gate `school:read`）

- KPI 卡：学生数 / 教师数 / 班级数（推导式只读，与 qiuqiu Dashboard 同模式，**不展示没有数据源的虚荣指标**）。
- 待办卡：待审教师申请数（仅 `teacher:create` 角色返回）、待审学生数、未处理学业预警数（`warning` 现有数据）。
- 快捷入口：其余三个管理页 + 常用教师页（出题工作台/判卷中心）。
- 数据源：**唯一的新后端端点**（见 3.4）。

**② `/admin/users` 教师与班级**（gate `class:create`；Tab 内按 `can()` 二次显隐）

- Tab 教师审批（gate `teacher:create`，即仅 admin）：申请列表 / 通过 / 驳回，调 `GET /teacher-applications`、`POST /{app_id}/approve`、`POST /{app_id}/reject`。
- Tab 教师账号（gate `teacher:create`）：教师列表（`GET /users/teachers`）、编辑（`PUT /teacher/{id}`）、任教班级分配（`POST /teacher/{id}/assign-classes`）。
- Tab 班级管理（gate `class:create`）：班级 CRUD（`/api/classes` 现有 5 端点）——今天班级只能靠数据导入建，这是唯一的管理补位。
- **学生管理不搬**：继续用 StudentsPage（教师也用它），只修按钮显隐（见 3.5）。避免同一套学生管理做两份。

**③ `/admin/school` 学校设置**（gate `school:update`，即仅 admin）

- 学校信息表单：`GET /api/school` / `PUT /api/school`。
- `POST /api/school`（建校）以「未初始化时显示初始化表单」的形态露出，不做独立流程。

**④ `/admin/logs` 操作日志**（gate `log:read`）

- `GET /api/logs` 表格 + 筛选（user_id / action / 时间段）。只读。
- 日志的**生产侧**由 3.4-③ 补齐（敏感动作落日志），本页是消费侧。

### 3.4 后端改动清单（P0 全部后端改动）

1. **新增 `app/api/admin_overview.py`**：`GET /api/admin/overview`，`PermissionChecker("school", "read")`。聚合：学生/教师/班级计数 + 待审数。待审教师数字段仅对 `can("teacher","create")` 的角色返回（academic_admin 看不到教师审批，字段就不下发，而不是下发 0）。
2. **`main.py` 注册新 router；`tests/test_permission_matrix.py` 的 `REFERENCE_ROUTERS` 加 `"/api/admin"`**（守卫测试会强制该 router 每个端点声明权限——这是本仓库的既有纪律）。
3. **`teacher_application.py` 整改**：GET 列表的门从 `teacher:read` 改为 `teacher:create`，删除函数体内 `role != "admin"` 检查（阶段 7.1 对 log.py 的同款整改：让矩阵重新成为唯一授权真源）。核查 approve/reject 两端点是否也是函数体检查，是则同款整改。
4. **`user.py` 敏感动作补审计**：`/teacher/approve`、`/student/approve`、`/student/{id}/transfer`、`/student/{id}/reset-password`、`DELETE /student/{id}`、`/teacher/{id}/assign-classes` 成功后直写 `OperationLog`（照 `app/services/data_import.py:33` 的直写模式，不走 HTTP `POST /api/logs`）。
5. **无矩阵改动、无新资源键、无新迁移**。

### 3.5 前端按钮显隐（清 403 账的正解）

原则：**按钮按能力显隐，而不是点了报 403**。前端已有 `can(permission)`（`lib/api.ts:163`，与后端 `permissions_for()` 同形）。

- `ExamPage`：删考试 `can("exam:delete")`、删题库/删题目 `can("exam_bank:delete")`——仅 admin 显示。
- `StudentsPage`：重置密码 `can("student:update")`（admin + academic_admin 显示）、新增/批量导入 `can("student:create")`、删除 `can("student:delete")`。
- 其他页面若有类似按钮，P0 顺手全查一遍：**grep 前端所有调 DELETE 类端点或 403 相关的按钮，逐一加 `can()` 门**。

### 3.6 测试与验收（goal-driven）

| 验证 | 标准 |
|---|---|
| 权限守卫 | `pytest tests/test_permission_matrix.py -q` 全绿（含新 `/api/admin` router） |
| 角色断言 | `test_permission_roles.py` 增补：academic_admin 调 `/teacher-applications` 必须 403、调 `/api/admin/overview` 200 且**无**教师待审字段；teacher 调 `/api/admin/*` 全 403 |
| 审计 | 新增用例：admin 重置密码后 `GET /api/logs` 出现对应记录 |
| E2E | 新增 `_e2e_verify.admin.py`（仿 `_e2e_verify.phase5.py`）：admin 登录落地 `/admin`、四页可达；teacher 登录看不到管理菜单；ExamPage 删题库 admin 可用、教师不可见 |
| 前端单测 | 菜单注册表快照 + 按钮显隐逻辑（vitest，仿 `frontend/tests/` 现有模式） |
| 超管场景 | superadmin 登录 → 未 break-glass 时 overview 返回明确提示（数据范围空集是 ADR-0011 设计行为，不是 bug；P0 只要求提示清晰，工作台在 P2） |

**P0 完成的定义**：教师端不再存在任何「点了 403」的按钮；admin 全部日常动作（审批/重置密码/删题库/学校设置/看日志）有界面；每个敏感动作在日志页可追溯。

## 4. P1 —— 内容运营界面（KB 治理）

### 4.1 范围

KB 运维今天 100% CLI 化：摄取 `kb_ingest`、词典 `kb_dictionary`、审校包落库 `kb_graph_import`、标签映射 `kb_tag_map_import`，老师终审靠**会话口头批准 + `_reviews.json` 落盘**。P1 把「审校 → 批准 → 落库」搬进界面。

- **P1a（先做，纯 DB 写，无嵌入模型依赖）**：审校包浏览与批准落库、词典/标签映射查看、摄取状态只读卡。
- **P1b（视部署环境）**：摄取触发界面。前提：部署机有嵌入模型（`EMBEDDING_CACHE_DIR` + bge-large-zh）。没有就永久 CLI，界面提供命令复制。

### 4.2 权限变更（P1 唯一的新键动作）

`knowledge` 资源键现有所有内容角色 `_R`（读文档列表）。追加：

```python
ROLE_PERMISSIONS['admin']['knowledge'] = ['read', 'update']      # 镜像自动带给 super_admin
# academic_admin / subject_lead / teacher 维持 ['read']
```

菜单：`{"key": "admin_kb", "resource": "knowledge", "action": "update"}`。

⚠️ 矩阵完整性断言会拦「没有端点消费的键」——`knowledge:update` 必须与消费它的端点同一批落地。

### 4.3 API 设计（新 router `app/api/kb_admin.py`，全部挂主进程）

| 端点 | 门 | 说明 |
|---|---|---|
| `GET /api/kb/status` | `knowledge:read` | 各册摄取状态、文档/chunk 计数、词典覆盖、上次评测阈值（推导式只读） |
| `GET /api/kb/review-packages` | `knowledge:read` | 审校包列表（`content/kb/*` 的提议边/词典 diff 结构化） |
| `POST /api/kb/review-packages/{id}/approve` | `knowledge:update` | 批准落库——**调 `kb_graph_import` 的服务层函数**，不复制逻辑 |
| `POST /api/kb/review-packages/{id}/reject` | `knowledge:update` | 驳回并留痕（替代口头否决） |
| `POST /api/kb/jobs` | `knowledge:update` | P1b：触发摄取/词典同步，立即返回 `job_id` |
| `GET /api/kb/jobs/{id}` | `knowledge:read` | 任务进度轮询 |

**长任务模式照抄 qiuqiu**：立即返回 jobId + 前端轮询；任务表落 `OperationLog`（谁在何时批准/触发了什么）。JOB 执行用 FastAPI `BackgroundTasks`/进程内线程池——**绝不另起进程碰 chroma/SQLite**（第 1.2 节约束）。

### 4.4 页面 `/admin/kb`（gate `knowledge:update`）

- 状态卡：六册摄取状态 / chunk 规模 / 词典覆盖 / 阈值水位（只读）。
- 审校队列：提议边列表，diff 视图（新增边/词典条目 vs 现状），批准 / 驳回。
- 任务面板（P1b）：摄取任务启动、进度条、历史。
- 老师终审语义升级：从「会话里口头批准 + `_reviews.json`」改为「界面批准落库 + 日志留痕」；`_reviews.json` 保留为导出产物，不再是批准的载体。

### 4.5 验收

- 界面批准落库的结果与 CLI `kb_graph_import` **对拍一致**（同一审校包两条路径落库后 `kb_eval` 结果相同）。
- `knowledge:update` 不出现在 academic_admin/subject_lead/teacher 的能力清单（`permissions_for()` 单测）。
- 批准/驳回/触发摄取三种动作都在 `/admin/logs` 可追溯。

## 6. 技术约束与风险

| # | 风险 | 对策 |
|---|---|---|
| 1 | `chemai.db` 被 uvicorn 锁定（HANDOFF 坑 10） | 一切管理 API 挂主 FastAPI 进程；禁止独立 admin 进程写库 |
| 2 | chroma 删集合与重摄必须同进程（坑 3） | P1b 摄取 job 用进程内 BackgroundTasks，不跨进程 |
| 3 | 超管数据范围默认空集（ADR-0011） | overview 对未提权 super_admin 返回明确空态提示；日常运营用 admin 账号 |
| 4 | 矩阵完整性断言拦「死键」 | 新资源键/新动作必须与消费端点同 PR 落地（P0 零新键，P1 仅 `knowledge:update`） |
| 5 | 前后端菜单版本不同步 | 前端对未知 key 已是「跳过 + console.warn 不崩」；发布顺序：先后端、后前端 |
| 6 | 概览页虚假数据损害信任 | 只做推导式真实数据；无数据源的指标不上卡（IntegrationPage 的 PlaceholderNotice 是范例） |
| 7 | 过度抽象 | 学生管理不搬页、不抽公共组件（AGENTS.md：两页演化方向不同，先各自独立） |

## 7. 工作量与节奏

参照 qiuqiu（~8,000 行 / 4 天）与 teaching-assistant（~6,800 行 / 1 天移植）——两者从零建了 CRUD 骨架与权限空白；本项目复用 RBAC + SPA 壳 + 现成 API，规模按砍半再砍半估：

## 8. 与参照项目的关系（一句话备忘）

- **qiuqiu 值得抄的**：异步 job + 轮询、非目标清单纪律、推导式只读 Dashboard、「后端 API 无法外包、前端可以外包」的判断（本项目对应为：复用 antd + 自有 ui 组件，不引 react-admin 第二套 UI 体系）。
- **qiuqiu/teaching-assistant 不抄的**：独立 admin 进程、单 token、无 RBAC（那是单人演示产品的形态）；人设/记忆/心情/RSS 页（陪伴玩具，与教学运营无关，teaching-assistant 11 页里约一半属此类过度设计）。
- **teaching-assistant 的教训**：它的后台一天建成是因为有母本可逐字照搬；本项目没有母本，但**有比母本更值钱的东西——权限矩阵、菜单机制、现成管理 API 全部就绪**，缺的只是页面。
