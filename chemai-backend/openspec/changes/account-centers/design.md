# Design: account-centers

## Context

- 学生：340 个账号，教师端 `/students` 是学情视角（正确率/障碍/诊断），无账号生命周期字段。
- 家长：`parents` 680 行、`student_parent_bindings` 680 行，但 `accounts` 中 parent 仅 2 个；`/api/parent/register` 与 `/api/parent/bind` 已存在（自助路径）。
- 教师：`AdminUsersPage` 已有「教师审批 + 教师账号」两 Tab，行为已验证。
- 班级：`class_api` 有 5 个 CRUD 端点；`grade.py` 有列表与创建；班级只能靠数据导入创建。

## Goals / Non-Goals

**Goals**
- 三类账号各有一页，字段与动作按"账号生命周期"组织
- 家长激活漏斗成为可执行入口（看完就能开通）
- 班级/年级可从界面创建

**Non-Goals**
- 不改教师端 `/students` 的行为
- 不替换家长自助注册（批量开通是并行渠道）
- 不做账号合并/去重自动决策（只标记异常，人工处理）

## Decisions

**D1 — 学生账号页字段以"账号"为准，不与学情混排。**
列表只带 1-2 个轻量学情指标（如最近活跃），正确率/障碍类型留在教师端，避免两页重复。

**D2 — 批量开通复用教师审批的凭据模式：服务端生成随机密码 → 响应返回明文一次 → 落库 SHA-256。**
不引入"家长自助激活码"新流程（自助注册已存在）。凭据用 Modal 展示并强制复制确认。

**D3 — 家长"有账号"判定 = `accounts` 中存在 `parent_id` 关联且 status=active。**
不新建冗余标志位，避免双写不一致。

**D4 — 绑定解绑 = 状态置 revoked，不物理删除。**
保留审计与历史；学生端查询只取 active。

**D5 — 异常视图用查询即时计算，不建物化表。**
680 条规模，三种异常（重复手机号 / 未激活 >7 天 / 一孩 >3 家长）都是小查询。

**D6 — 班级页把年级 CRUD 一起做，因为建班必须选年级。**
`grade.py` 已有创建端点；补更新/删除（删除仅当无班级）。

**D7 — 组织树用两级展开列表而非树组件。**
年级 → 班级两级，用可折叠分组即可，不引 Tree 组件。

## Risks / Trade-offs

- [批量开通给 680 位家长发密码不现实] → 默认按筛选结果小批量（≤50）操作；大批量走"导出名单 + 线下通知"，页面提示。
- [`Parent` 表可能没有 `status` 字段] → 实施首任务核对 schema，缺则补列 + 迁移（幂等）。
- [停用学生影响教学] → 停用前显示"该生有进行中的练习/待确认门"提示，不强制阻断。
- [班级删除误伤] → 非空班级必须二次输入班级名确认。

## Migration Plan

1. 补 schema（`Parent.status` 若缺）+ 迁移
2. 后端：账号中心 router + 批量开通 + 绑定管理
3. 前端：三页 + 教师页拆分
4. 回归 + e2e
5. 回滚：新端点与页面纯增量；`Parent.status` 补列可保留（不影响旧代码）
